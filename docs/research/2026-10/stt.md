# STT options for Qorğan — research report (2026-10-07)

Scope: on-device, browser-first ASR for KK / RU / KK–RU code-switching (+EN), 100–300 MB budget, no network, phones later via eGov WebView or native. Everything below was verified today against the HF API (`/api/models/<id>?blobs=true`), the GitHub releases API (sherpa-onnx `asr-models`, 499 assets), alphacephei `model-list.json` + HTTP `Last-Modified`, the Bing voices endpoint, PyPI JSON, `datasets-server`, or the cited page. "Conf." = my confidence in the fit assessment.

## 0. Headline findings

1. **Vosk shipped new Kazakh models on 2025-10-06** (`vosk-model-small-kz-0.42`, 57 MB; `vosk-model-kz-0.42`, 1.3 GB). The old `small-kz-0.15` you run is flagged `obsolete`. Published WER (small): FLEURS 21.10, CV17 30.0, KSC 9.7, KSC-other 24.86; big: 13.09 / 12.50 / 4.49 / 18.51. Apache-2.0. This is the cheapest win available.
2. **sherpa-onnx WASM is single-threaded** (`wasm/asr/CMakeLists.txt`: `INITIAL_MEMORY=512MB ALLOW_MEMORY_GROWTH=1 --preload-file`, no `USE_PTHREADS`). It needs no COOP/COEP, so it is the only browser path that will also work inside the eGov **Android WebView**, where `crossOriginIsolated` is false by design (Google: one renderer per app). Vosklet's threads are the blocker there.
3. **Russian has moved on without Vosk-Kaldi**: alphacep's own `vosk-model-small-streaming-ru` (Zipformer2, icefall, CV-ru WER 11.3, Apache-2.0) is already republished as `sherpa-onnx-streaming-zipformer-small-ru-vosk-int8-2025-08-16` (**23 MB tar, 25 MB int8 encoder**). T-Bank's **T-one** (71M, 8 kHz telephony, streaming CTC, Apache-2.0) is in sherpa-onnx too (122 MB fp32) and reports WER 7.94 on OpenSTT `asr_calls_2_val` vs 20.82 for Whisper-large-v3.
4. **The right code-switching design is a single joint-vocabulary KK+RU model, not per-utterance voting.** It exists: `nvidia/stt_kk_ru_fastconformer_hybrid_large` (115M, CC-BY-4.0, KSC2 read 4.43 / spontaneous 15.25, Golos crowd 2.46). A CTC-only ONNX export is 437 MB fp32; a MatMul-only int8 should land ~110–130 MB (sherpa's comparable 10-language FastConformer int8 is 97.5 MB). It is non-streaming, which matches your per-utterance VAD flow.
5. Kazakh is **not available offline on any native stack** (iOS 27 on-device dictation, SpeechAnalyzer, Android Live Caption/Transcribe all list Russian but not Kazakh). Native mobile for KK means bring-your-own model (sherpa-onnx Android/iOS, Vosk, or CoreML — TilQazyna already published a CoreML kk-ru FastConformer CTC, 214 MB).

**sherpa-onnx WASM specifics:** offline builds (`vad-asr`) and online transducer/CTC builds share the same flags; models are `--preload-file`d into the `.data` bundle (so multi-100 MB bundles are one fetch; you can also patch the loader to fetch lazily). Pre-built HF Spaces exist only for zh/en ASR, VAD and TTS — none for ru/kk, so you build. No KK model has been converted for sherpa; alphacep has already pushed bn/ru/uz streaming zipformers to HF (`alphacep/vosk-model-small-streaming-{ru,bn,uz}`), so a `kz` one is a realistic ask.

## 2. Code-switching: what the literature and the models say

- **KSC2** (Interspeech 2022; MIT on HF, CC-BY-4.0 on ISSAI site) is the only public KK corpus with CS. CS *sentence rate* is low: 1.9 % in KSC read train/test (7.1 h / 3,333 utt test), 10.2 % TV programs (spontaneous, 0.7 h test), 5.8 % radio (0.9 h test), 3.7 % parliament. Baseline streaming Transformer: 6.3 % WER on KSC test, 27–37 % on spontaneous sources. Rule used: a Kazakh stem with a Russian suffix counts as Russian and vice-versa — adopt this for your own labelling.
- **STC/ITMO 2020 (CEUR Vol-2590 short13)**: training one bilingual model on monolingual KK + RU data (no CS training data) cut WER on *embedded Russian words* inside Kazakh speech from 59.53 to 44.84 (−14.69 abs) and on matrix Kazakh words 51.66→49.87, at the cost of RU-only WER (31.91→37.42). This is the direct evidence that **a joint model beats per-language models for mid-sentence switches**, which is exactly where per-utterance voting cannot win.
- **ISSAI 2021 (arXiv 2108.01280, SPECOM)**: one Transformer for kk/ru/en scored 20.5 % avg WER vs 20.9 % for three monolingual models; recipes, data and models released (ESPnet). Combined grapheme set worked.
- 2024–26 work is mostly MT for CS text (arXiv 2503.20007, kazRush). On HF, **TilQazyna** (May–Aug 2026) is actively training Qwen3-ASR checkpoints named `training-qwen3-v2-with-code-switching` / `v3-only-code-switching` and published a CoreML `stt_kk_ru_fastconformer_ctc_e2e` (no cards, no licences yet) — worth a direct contact; they look like a Kazakh state language body.
- **Practical rule:** keep voting only as a fallback; the primary should be a model whose *tokenizer* is joint (nvidia kk-ru SentencePiece-1024, nur-dev BPE-4096, alibiserikbay 47-class Cyrillic CTC). None of the three publishes a CS test set; you will have to build one (Section 5).

## 3. Native mobile and WebView constraints

- **iOS (Apple feature-availability, iOS/iPadOS 27):** server Dictation lists Russian *and Kazakh* (new); **on-device dictation** lists Russian, not Kazakh; `SpeechTranscriber.supportedLocales` (SpeechAnalyzer, iOS 26+) = 42 locales / 22 languages incl. `ru_RU`, **no kk**; Live Captions: neither. `SFSpeechRecognizer.supportsOnDeviceRecognition` follows the on-device dictation list → RU yes, KK no.
- **Android:** `RecognitionSupport` (API 33) exposes `getSupportedOnDeviceLanguages / getInstalledOnDeviceLanguages / getPendingOnDeviceLanguages / getOnlineLanguages`; `SpeechRecognizer.createOnDeviceSpeechRecognizer` (API 31). Google does not publish the offline list; Live Caption on Pixel 6+ ships Russian (and 14 others), not Kazakh; Live Transcribe offline packs exist on Pixel/Android 12+ but Kazakh appears nowhere offline. Kazakh is online-only (Google app) → violates the no-network invariant.
- **WebView:** Android WebView has `crossOriginIsolated === false` regardless of headers (Chromium 40914606; Google: single renderer per app). A Sept 2026 probe on WebView 152 found `WebAssembly.Memory({shared:true})` and `Atomics.wait` work but the `SharedArrayBuffer` global is undefined and structured-cloning it is gated, so Emscripten pthreads are unreliable → **Vosklet will not run in the eGov WebView; single-threaded sherpa-onnx WASM will.** iOS WKWebView: COOP/COEP via `WKURLSchemeHandler` gives `false`; the same headers from a loopback HTTP server give `true` with SAB defined. Native fallback on both: sherpa-onnx has Android AAR / iOS (Swift) bindings running the same ONNX files, so a Kotlin/Swift shim can share models with the PWA.

## 4. Telephone-channel simulation and KK/RU test speech

**Degradation chain (all offline, MIT):** `audiomentations` 0.43.1 — `BandPassFilter(300–3400 Hz)`, `Resample`/`Aliasing` (8 kHz round-trip), `BitCrush`, `Mp3Compression`, `RoomSimulator` (pyroomacoustics 0.10.1 backend) for the speakerphone room, `AddBackgroundNoise`, `ApplyImpulseResponse`, `TanhDistortion`, `Limiter`, `Gain`. Codecs through ffmpeg (`torchaudio.io.AudioEffector` or a subprocess): `libgsm` (GSM 06.10, 8 kHz), `libopencore_amrnb` (AMR-NB 4.75–12.2 kb/s — the real mobile-voice codec in KZ), `libopus` 8–24 kb/s (VoLTE/WhatsApp), `g722`. Order: TTS → room IR (far-end phone speaker → room → your mic) → band-limit → codec → noise. T-one's `asr_calls_2_val` numbers tell you what "good" looks like on real 8 kHz calls (7.9 % WER).

**Open TTS, verified today:**
- `edge-tts` 7.2.8 voice list: `kk-KZ-AigulNeural` (F), `kk-KZ-DauletNeural` (M), `ru-RU-SvetlanaNeural`, `ru-RU-DmitryNeural`. Online, Microsoft consumer endpoint — fine for internal test audio, do not redistribute the WAVs.
- **Piper** (`rhasspy/piper-voices`, MIT voices; engine GPL-3): `kk_KZ-issai-high` 122 MB, `kk_KZ-iseke-x_low` / `kk_KZ-raya-x_low` 27 MB (from ISSAI KazakhTTS2); `ru_RU-{denis,dmitri,irina,ruslan}-medium` 60 MB each. Fully offline; sherpa-onnx also runs them.
- Vosk-TTS ru (`vosk-model-tts-ru-0.4-{natasha,irina}` 116 MB, Apache-2.0; `0.9-multi` 747 MB).
- Not usable: XTTS-v2 (CPML non-commercial; ru yes, kk no), Fish-speech 1.5 / S1-mini (CC-BY-NC-SA; ru yes, kk no), Kokoro-82M (card: `en` only).
Speaker diversity for KK is 3 offline voices + 2 edge voices — add pitch/tempo perturbation and treat results as a smoke test, not a WER claim.

## 5. Honest WER recipe (equal footing, Python or Node)

Test sets (sizes verified): **FLEURS** `google/fleurs` (CC-BY-4.0, ungated): `kk_kz` test **856** utt (train 3,200 / val 369), `ru_ru` test **775**; **KSC2** (`issai/Kazakh_Speech_Corpus_2`, WebDataset tars): KSC read test 7.1 h / 3,333 utt + the CS-rich spontaneous tests (TV 0.7 h, radio 0.9 h, podcasts); **OpenSTT** `asr_calls_2_val` 7.7 h / 12,950 utt, 16 kHz WAV from 8 kHz calls (CC-BY-NC; Azure blob) — RU telephony reference; **Golos** test via `bond005/sberdevices_golos_{10h_crowd,100h_farfield}`; Common Voice 17 `kk` is gated and ~1 h total (NVIDIA used 1 h train) — report it but do not tune on it. EN: LibriSpeech test-clean (Vosk en small 9.85) or FLEURS `en_us`.

Normalisation (apply to ref and hyp identically; keep one shared `normalize.py` and port it to JS): NFC → lowercase → `ё→е` → strip punctuation/hyphens except intra-word apostrophe → collapse whitespace; digits: convert ref numbers to words with `num2words` (ru/kk supported?) or drop utterances containing digits and say so. Compute with `jiwer` 4.0: `jiwer.wer(refs, hyps)` plus `jiwer.process_words` for S/D/I; also **CER** (Kazakh agglutination makes WER harsh). Report a 95 % bootstrap CI over utterances (1,000 resamples) next to the point estimate, mirroring your Clopper–Pearson habit for FPR. Add the two project metrics that matter more than WER: **cue survival** (share of lexicon cue spans recovered on the degraded audio, your existing harness) and **downstream risk delta** (score with reference vs score with hypothesis).

Engines: Python — `sherpa-onnx` 1.13.8 (`OnlineRecognizer`/`OfflineRecognizer`), `vosk` 0.3.45, `onnx-asr` 0.12.0 (NeMo CTC/TDT, Parakeet, GigaAM, T-one exports). Node — `sherpa-onnx-node` (same ONNX files) or, better, your existing Playwright bridge so the number comes from the *browser* build (your ADR D32/D33 lesson applies to ASR too: server ORT ≠ browser ORT). Feed streaming engines 300 ms chunks with the final result after `input_finished()`; feed offline engines your VAD segments, not whole files.

## 6. Three experiments to run first (ranked)

1. **Vosk kz 0.15 → 0.42 in Vosklet (3–6 h).** Confirm Vosklet loads the 0.42 graph; re-run the real-ASR capture harness (cue recovery, 0/160 false-fire gate); compute FLEURS-kk and KSC-test WER for 0.15 vs 0.42 with the recipe above. Produces: first honest KK WER pair for the shipped stack and a cue-recovery delta. Zero architecture risk; +16 MB.
2. **sherpa-onnx single-thread WASM for Russian: zipformer-small-ru-vosk-int8 (25 MB) then T-one (self-quantised int8) (12–20 h).** Build `build-wasm-simd-asr.sh` with each model; run inside Playwright (desktop) and in an Android WebView test app; measure RTF, memory, WER on `asr_calls_2_val` (1k-utt subset) and FLEURS-ru, cue survival on your degraded synthetic calls. Produces: RU WER/RTF for two engines, and a yes/no on the eGov WebView without COOP/COEP (removes the Vosk-threads blocker; also replaces `small-ru-0.22` from 2021).
3. **Joint KK+RU model per utterance: `nvidia/stt_kk_ru_fastconformer_hybrid_large` CTC → MatMul-only int8 ONNX → sherpa-onnx offline (Node first, then WASM) (16–30 h).** Build a 300-utterance code-switch test: KSC2 TV/radio test utterances flagged CS (by the suffix rule) + Piper/edge-tts synthesised scam lines with mid-sentence switches, degraded via the Section 4 chain. Compare against today's voting on WER (kk, ru, CS), cue survival and risk delta; log size and RTF. Produces: the first CS number and a go/no-go on replacing voting with one ~120 MB model. If it wins, the follow-up is a licence conversation with nur-dev (streaming TDT, same architecture) or a NeMo retrain on KSC2 + Golos + your CS data (public recipe, ~40–80 GPU-h).

## 7. Dead ends (verified)

- Whisper in-browser (transformers.js large-v3-turbo q4f16 ≈ 540 MB; whisper.cpp WASM ≤ small, 120 s cap; zero-shot KK FLEURS WER 31–33 %; KRASR small fine-tune 465 MB ggml, your 0.54/0.72). Keep Whisper fine-tunes server-side as a labeller.
- Parakeet-TDT 0.6B v3 / Canary-1b-v2: no Kazakh; 622 MB int8 encoder; browser builds exist but irrelevant.
- Moonshine, Kyutai STT: no RU/KK. SeamlessM4T-v2, MMS-1b-all: non-commercial, >1B. Cohere transcribe: 1.6 GB. Gemma 3n: gated, LLM-sized.
- Omnilingual ASR 300M: 280–350 MB, non-streaming, no published KK WER; Dolphin-base: 77 MB but FLEURS kk 31.5 (worse than Vosk-kz small 21.1), non-streaming.
- Qwen3-ASR kk-ru-en fine-tunes (1.5 GB, CC-BY-NC) — server only.
- Web Speech API, Google online kk-KZ, Apple server Dictation: all send audio off-device.
- Apple/Google *offline* native recognisers for Kazakh: none exist (RU yes on both).
- Vosklet (WASM threads) inside Android WebView: blocked by missing cross-origin isolation.
- 8-language streaming zipformer with ru (283 MB int8) and GigaAM-v3 (214 MB int8): over budget for one language, no kk.
- Common Voice kk as a tuning set: ~1 h, gated; evaluation only.

Unverified / lower confidence: exact int8 sizes for T-one and the NVIDIA CTC export (estimates from comparable sherpa exports); whether Vosklet 1.2.1 loads the 0.42 graph unchanged; `onnx-asr` T-one support (README claim not re-checked); Omnilingual KK quality.
